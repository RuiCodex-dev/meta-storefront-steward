# Storefront Steward: design

Status: design only, written 2026-10-18 before the event. No project code exists. Linear RUI-268.

## 1. The pitch in one paragraph

Rui Codex is one person with 19 apps and games on Google Play (some also on the App Store), listed in many languages.
Every release cycle costs a day of the same loop: read reviews in languages the developer does not speak, match them to
crash and ANR data and to the release that caused them, then write replies, release notes and new screenshots.
**Storefront Steward** does that loop as an agent that runs on the developer's own store data. A small open-weights
model, fine-tuned by distillation from Muse Spark, triages every review for almost nothing. Muse Spark reads a whole
app's feedback in one 1M-token context, merges the same issue across languages, links it to crash clusters and the
release that introduced it, and drafts replies and release notes in which every sentence cites its evidence. SAM 3.1
and Muse Image produce store screenshots whose app UI is provably the real UI, pixel for pixel. Nothing is posted
until the developer clicks Approve.

Judging fit:

| Criterion | Weight | How we score |
|---|---|---|
| Impact | 30 | a real problem for millions of indie developers; shown on a real studio's real data; measured hours saved |
| Use of Meta AI tooling | 25 | five Meta models with distinct jobs: distillation Spark -> Glimmer, 1M-context clustering with prompt caching, Spark video understanding for bug reproduction, SAM 3.1 on images and video, Muse Image with a pixel-fidelity guard |
| Technical depth | 20 | held-out evaluation with confidence intervals against baselines, citation verifier, privacy layer, cost and latency receipts, tests |
| Demo | 25 | live run on production data, a real approved reply posted on camera, a 3-minute video made with real footage only |

## 2. What the agent does (user-visible)

1. **Inbox.** One table of every review, rating, crash/ANR issue and store-review note across all apps, pseudonymised.
2. **Triage.** Each item gets a category (`bug`, `crash`, `performance`, `feature_request`, `billing`, `ads`,
   `ux_confusion`, `praise`, `spam_or_offtopic`), severity 1-4, language, app version, and a one-line English gloss.
3. **Issue board.** Cross-language clusters ranked by users affected x severity x recency. Each cluster shows the
   reviews it contains (with translations), the linked crash/ANR issue, the suspected release (first version where the
   cluster appears), and a confidence.
4. **Drafts.** Per review: a reply in the reviewer's language and the developer's tone, within store limits (Play 350
   characters). Per release: release notes per locale that say only what the changelog supports. Every claim carries a
   citation chip (review id, crash issue id, release, commit) that the verifier has checked.
5. **Screenshots.** For a chosen app and locale: real screens captured from the app, the UI cut out by SAM 3.1, a
   background and frame generated by Muse Image, captions in real typography, and a fidelity badge proving the UI
   pixels are identical to the capture.
6. **Approval queue.** Approve, edit or reject. Approve calls the store API (`reviews.reply` or
   `customerReviewResponses`); everything is logged. Default mode is dry-run.
7. **Receipts.** Every model call: model, mode (Standard), tokens, cost, latency, redacted prompt hash.

Stack: Python 3.12, FastAPI, SQLite (one file), HTMX with server-rendered templates (no build step), OpenAI Python SDK
pointed at `https://api.meta.ai/v1`, `google-api-python-client` for Play, PyJWT for App Store Connect, Pillow and
NumPy for compositing, pytest. Training: Axolotl or TRL+PEFT on Modal. Node only for `@meta-sam/parser` if a Python
decoder is not trivial (the mask payload is documented, so a Python decoder with a round-trip test is preferred).

## 4. Data flow and model roles in detail

### 4.1 Triage by distillation (Spark teacher -> open-weights student)

- **Teacher:** Muse Spark 1.3, Standard mode, structured output with a strict schema, `reasoning_effort: low`, a long
  cached system prompt holding the label guide and 30 worked examples. It labels the training pool.
- **Gold set:** 600 items drawn stratified by app, language and star rating, labelled by the owner in a labelling page
  (keyboard shortcuts, about 2 hours; the teacher's label is hidden until the owner commits, to avoid anchoring).
  300 are dev, 300 are a frozen **test** set nobody trains or prompts on.
- **Students:**
  - **S1: Muse Glimmer 30B + QLoRA** (Apache 2.0, text + image; recipe verified by Meta on 1x H100; LoRA rank 16,
    alpha 32, lr 2e-4, 3 epochs, as in the Meta post-training guide).
  - **S2: Llama 3.2 3B Instruct + LoRA** (text-only, cheap, fast cold start; the live-demo fallback).
- **Baselines:** Spark zero-shot, Spark 30-shot (the teacher itself), Glimmer zero-shot, Llama 3B zero-shot, and a
  keyword/regex rule baseline so the table has a floor.
- **Output format:** the student emits a compact JSON object; constrained decoding (vLLM guided JSON) guarantees parse.
- Why it matters: per-review cost goes from Spark prices to near zero, latency drops, and the triage model can run
  privately on the developer's own hardware. That is the "free up time" theme in practice.

### 4.2 Long-context clustering (Spark, 1M tokens, prompt caching)

No vector database. For each app, all triaged items of the last 90 days (typically 5k-150k tokens for an indie app) go
into one Spark context, ordered and id-tagged, followed by the release list and crash issue summaries. Spark returns
clusters as structured output: `{cluster_id, title_en, item_ids[], languages[], linked_crash_issue_ids[],
first_seen_version, evidence_quotes[{item_id, quote}]}`. The context prefix is stable between runs, so repeated
questions ("what changed since 2.3.1?", "draft notes for 2.3.2") are billed at the cached rate ($0.15/M instead of
$1.25/M). This is a deliberate showcase of a Meta-specific capability: whole-corpus reasoning with citations instead
of retrieval.

Guard: every `item_id` and every `evidence_quote` is checked by string match against the source; clusters with an
invented id or quote are rejected and re-asked once, then dropped and logged.

### 4.3 Crash and release linking

Deterministic first: version codes and dates from Play tracks / App Store versions, crash issue first-seen versions
from the Reporting API, review app versions from the review records. Spark only proposes links; the code accepts a
link only if the versions line up (cluster first seen in version N and the crash issue first seen in N, or within one
version). The board shows which rule accepted the link.

### 4.4 Drafting replies and release notes

- Reply drafts: Spark, structured output `{reply_text, language, cites[], promises[]}`; the verifier rejects drafts over
  350 characters (Play), in the wrong language (fastText-style language ID locally), with uncited claims, with
  promises of dates or refunds, or containing anything that looks like personal data.
- Tone: the owner's 20 past replies (if any exist) are the style examples; otherwise a short style guide he approves.
- Release notes: only from the actual changelog (git log of the app repo, read locally, never uploaded) plus resolved
  clusters; each line cites a commit or cluster.

### 4.5 Bug reproduction with video understanding (stretch, high value for "unexpected capabilities")

For a top cluster, Spark turns the reviews into a short reproduction script (taps and waits). The script runs on an
Android emulator (adb input), the screen is recorded (adb screenrecord, 20-40 s), and the recording goes to Spark as
video input with the question "does the symptom described in these reviews occur? cite the timestamp". SAM 3.1 on the
same video tracks the relevant UI element (for example "loading spinner") to measure how long it stays. The board then
shows "reproduced at 0:14" or "not reproduced". **The emulator must be offline from live game backends** (lesson from
the 2026-10-15 IFT league incident): use a test build or airplane mode.

### 4.6 Store screenshots with a fidelity guard

1. Capture real screens from the app (emulator, existing store-refresh captures in
   `0RuiCodex Games & Apps\_store_refresh_2026-10\<app>\captures` may be reused as inputs; they are our own assets).
2. SAM 3.1 segments "phone screen" / "app interface" to get a clean mask of the UI region and removes status-bar noise.
3. Muse Image generates only the scene: background, lighting, device frame shell, using the app's palette as a
   reference image. It never receives instructions to redraw the UI.
4. Our compositor pastes the **original captured pixels** into the frame (affine fit only, no resampling of the UI when
   the target size matches; otherwise one documented Lanczos resize).
5. **Fidelity guard:** the UI region of the output is compared against the source capture (after the same resize):
   SSIM >= 0.999 and a perceptual hash match, or the asset is rejected. Captions are rendered with real fonts by our
   code, never by the image model.
6. Output sizes follow Play (phone, 7", 10", 1024x500 feature graphic) and App Store (6.9", 13") specs.

This turns "AI screenshots" into a trustworthy tool, and it follows Apple's rule that screenshots must show the app in
use.

## 5. Privacy and safety design (summary; full plan in `03-DATA-PLAN.md`)

- Pseudonymise before any model call; models never see reviewer names or store user ids.
- Standard mode only; Contributor mode never used for review data.
- Raw data and the re-identification map stay in `data/` (git-ignored) on this machine.
- Every outbound text is re-scanned for PII.
- Human approval for every store write; dry-run by default; per-action audit log.
- Demo video and any public material show pseudonyms only and blur nothing that would need blurring, because nothing
  identifying is ever rendered.

## 6. Evaluation plan

All numbers are reported with their denominators and 95% bootstrap confidence intervals. The test set is frozen before
any prompt or training run touches it, and its hash is committed.

| # | Question | Metric | Method | Target to claim success |
|---|---|---|---|---|
| E1 | Is the fine-tuned student good? | macro-F1 on category; accuracy on severity (+-1); language ID accuracy | 300-item owner-labelled test set; students vs Spark zero-shot, Spark 30-shot, Glimmer/Llama zero-shot, rule baseline | S1 within 3 points of Spark 30-shot macro-F1 and above Spark zero-shot; report honestly whatever happens |
| E2 | Is it cheaper and faster? | $ per 1,000 items; p50/p95 latency | receipts | >= 20x cheaper than Spark 30-shot |
| E3 | Are clusters right? | pairwise precision/recall and cross-language merge rate vs owner-built clusters | owner clusters 2 apps by hand (about 1 hour) | pairwise F1 >= 0.8 |
| E4 | Are citations real? | share of citations that exist and support the sentence | automatic id/quote check + owner spot check of 50 | 100% exist (guard), >= 95% support |
| E5 | Are drafts usable? | share of reply drafts the owner approves **without edits**; normalised edit distance for edited ones | blind review of 60 drafts in the approval queue | report the number; no target set in advance beyond ">= 50% unedited" as a hope |
| E6 | Does it save time? | minutes per release cycle | owner's stopwatch: one app's review+reply+notes cycle done manually (baseline) and with the tool, two apps each | report minutes saved with n stated; no extrapolation beyond "per cycle on this studio" |
| E7 | Are screenshots faithful? | share of outputs passing the fidelity guard; SSIM of UI region | automatic | 100% of shipped assets pass by construction; report the reject rate |
| E8 | Does repro work? (stretch) | reproduced / not reproduced vs owner judgement on 5 clusters | manual | report |

Honesty rules for the evaluation: no number without its n; no extrapolation to "all indie developers"; if the student
loses to Spark, the write-up says so and explains the cost trade-off.

## 7. Demo storyline (3:00 video; the live demo follows the same path)

All footage is real screen recording of the running product on real (pseudonymised) data. No mock-ups, no
fake UI, no AI-generated face. Voice: natural narration (owner's own voice if he wants, otherwise a synthetic voice
disclosed in the description); captions as .srt. Made with HyperFrames.

| Time | Scene | What is shown |
|---|---|---|
| 0:00-0:15 | The problem | The real Play Console of Rui Codex: 19 apps, reviews in many languages; one line: "one developer, no community team" |
| 0:15-0:40 | Ingest | Live run: connectors pull this week's reviews and vitals; the privacy layer turns names into pseudonyms on screen |
| 0:40-1:10 | Triage | Items stream in, tagged by the fine-tuned Glimmer student; cut to the evaluation table (student vs Spark vs baselines, cost per 1k) |
| 1:10-1:45 | One issue, many languages | A real cluster (whatever the data contains on the day; the "level-12 freeze" in the application was an illustration) with reviews in several languages, the linked crash issue and the release that introduced it; citations clickable |
| 1:45-2:10 | Reproduction (if E8 works) | Spark watches the emulator recording and marks the timestamp; SAM 3.1 tracks the element |
| 2:10-2:35 | Drafts and approval | Replies in the reviewers' languages with citation chips; the owner approves one and it is posted live through the Play API; release notes for the fix |
| 2:35-2:52 | Screenshots | Real capture -> SAM cut -> Muse Image scene -> composite with the fidelity badge, side by side with the source |
| 2:52-3:00 | Results | Hours saved per cycle, macro-F1, cost per 1k, "nothing posted without a human click" |

Live demo for judges: a hosted read-only instance on a pseudonymised snapshot (writes disabled), if the owner approves
hosting; otherwise the video plus a recorded unedited run.

## 8. Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Meta Model API not enabled in Belgium | medium | blocking | smoke test at kickoff; if blocked, ask in Discord office hours on day 1; fallback: Spark via a partner only if the rules allow, otherwise Glimmer/Spark Open on Modal/Baseten (open weights are allowed) |
| Official Rules forbid something in this design (public repo with data, prior assets, partner models) | medium | high | rules read first on 10-26; the design keeps data out of the repo and uses only new code |
| Too few own reviews with text to fine-tune (indie apps) | **high** | medium | count on day 1; pool all 19 apps and full CSV history; add Spark-generated synthetic items (marked, never in test); third-party public review sets only if CC0/CC-BY confirmed; the test set is always our own real reviews |
| Partner GPU credits not granted | medium | medium | Llama 3.2 3B LoRA trains on the local RTX 4070 8 GB in under an hour (owner OK needed for local GPU load); Glimmer only if credits arrive |
| 30B student too slow or costly to serve live | medium | medium | live demo uses S2 (3B) or a pre-warmed Glimmer endpoint during recording; batch triage uses whichever is cheaper |
| Play `reviews.list` only covers 7 days | certain | low | history from the GCS monthly CSV export; needs bucket access for the service account |
| Store rejection notes not in APIs | certain | low | manual import of the owner's rejection e-mails/messages (copy-paste or .eml), or skip; not core to the demo |
| Posting a live reply on camera goes wrong | low | medium | dry-run rehearsal; post only to a review the owner chose; reply text approved by the owner first |
| Muse Image alters UI or adds text | medium | high (honesty) | it never receives the UI; fidelity guard rejects; captions by our renderer |
| Privacy leak into video, repo or Meta | low | high | pseudonymise before models; outbound PII scan; repo has no data; video reviewed frame by frame before upload |
| Time: 10 days, solo, other hackathons in parallel (Open Agent 10-22..27, Airwallex to 11-13, Game Jam to 11-07) | high | high | strict cut list (below); stretch features only after the core demo path is recorded once |
| API key or service-account leak | low | critical | keys read at runtime from `.ruicodex-keys` or the existing service-account path; `.gitignore`; secret scan before every commit |
